# .scratch 工作规则

本目录保存跨会话工作项：设计快照、研究、实施 tickets、原型和验收证据。它不是实现或 API 的权威——当前行为以源码与测试为准（若存在 `docs/`，维护规则见 `docs/AGENTS.md`）。本文件只规定在这里怎么工作。

源码尚未落地时，`.scratch/active/` 是进行中设计的主要依据；随源码落地，代码与测试优先于这些笔记。

## 工作项结构

每个 `active/<work>/` 是一个目录，以一份简短的 `README.md` 作为唯一续作入口，覆盖五项：状态、最近核对日期、当前前沿（谁在做什么、卡在哪里）、完成条件、正式文档出口（工作项收尾时持久结论落到哪里）。

```
active/<work>/
├── README.md      # 续作入口（上述五项）
├── DESIGN.md      # 收敛后的设计快照——照着实现的形态
├── issues/        # tracer-bullet 实施 tickets，一文件一票
│   ├── 01-<slug>.md
│   └── 02-<slug>.md
├── materials/     # 研究与外部材料（只留值得重读的）
└── validation/    # 人工确认的验收证据
```

## Ticket 纪律

每个 `issues/NN-<slug>.md` 用固定骨架，按依赖顺序（阻塞者在前）从 `01` 起编号：

```markdown
# NN — 标题

**What to build:** 这张票完成后可端到端演示的行为（用户视角，不是分层任务清单）
**Blocked by:** 阻塞它的票号，或 "None — can start immediately"
**Status:** pending | ready | in-progress | complete

- [ ] 验收标准 1
- [ ] 验收标准 2
```

- **垂直切片**：每张票纵向打穿所有层，做完即可独立验证；不按层横向分工。
- **票自包含**：新会话不读整个工作项历史也能开工。避免具体文件路径和代码片段（会过期）；例外：原型里结论密集的片段（状态机、类型形状）可内联并注明出处。
- **前沿推进**：阻塞全部完成的票构成前沿、可立即开工；串行链自上而下执行。已写出但仍有未完成阻塞的票停在 **pending**，保证 `ready` 永远等于现在就能开工。
- **大范围重构例外**：一个机械改动波及全仓时，不硬塞进 tracer bullet——按 expand–contract 排序：先扩展（新旧并存），分批迁移，再收缩（删除旧形态）。

## 生命周期

- **收口一个工作项**：关闭或删除未完成的票 → 把持久结论移入维护文档（`docs/` 存在时）→ 删除没有溯源价值的过程材料 → 移入 `archive/YYYY-MM/`。
- **归档即历史**：归档中的状态与术语只代表当时的工作上下文，从不覆盖当前实现；不为迁就新代码回写归档。
- **临时产物**：日志、调试输出、下载物放 `local/`（gitignored），不进 active 或 archive。

## Git 跟踪

只提交已收口的工作记录；进行中的不提交。

- **`active/` 与 `local/` 保持不跟踪**（见根 `.gitignore`）。active 里的笔记一天变很多次，结论尚未脱敏；提交它会把半成品状态冻结进历史，混入从未清理过的材料。
- **工作记录先脱敏、归档、然后才提交**——通常 amend 进它所对应的有实质工作的那个提交，让记录随它解释的改动落地，而不是一条独立的"docs"提交。
- `active/` 里的文件不持久：工作项收口后整体移入 `archive/`。指向 `active/` 的链接不可依赖——指向 `archive/` 或维护文档。本目录 `README.md` 可以用文字（而非链接）提及 active 条目。
